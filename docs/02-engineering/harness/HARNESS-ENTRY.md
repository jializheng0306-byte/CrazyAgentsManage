# CrazyAgentsManage Harness Entry

## Purpose

This repository adopts the same high-level separation proven in `FlowMindDeploy`, but with a different orchestration surface:

- `Codex ↔ HermesAgent group collaboration` replaces `dual-cli`
- `OMX` remains the runtime/session substrate
- `harness/` remains the durable repository learning layer

## Required Artifacts For A Collaboration Round

Every non-trivial Codex ↔ HermesAgent round should leave behind:

1. one runtime state snapshot under `.omx/`
2. one Hermes handoff packet generated by script
3. one durable repository artifact when the round changes shared project truth
4. one harness success/failure record at closeout
5. one harness closeout artifact that binds trace / critic / governance / worktree lane
6. one PRD/roadmap update when the iteration changes implementation or operations truth
7. when a round needs combined governance evidence, read it in the shared order defined by FlowMind's governance evidence index rather than ad hoc picking single deploy or change artifacts

## Semantic-First Reading Rule

当任务涉及：

- `candidate`
- `promise`
- `truth`
- `trace`
- `review`
- `feedback`

Harness 要求先执行 [SEMANTIC-FIRST-READING-RULE.md](./SEMANTIC-FIRST-READING-RULE.md)：

1. 语义与契约层
2. 双仓产品与协同层
3. Hermes 宿主平台运行与运营层
4. 最后才进入原始实现层

这条规则的目的，是把双仓协同与 Hermes 宿主平台联动收敛为同一套前置读取顺序，而不是让不同 agent 各自从脚本、页面或群聊里推断事实。

## Harness Runtime Commands

Canonical repository-owned closeout and learning commands:

```bash
node scripts/harness-closeout-writeback.cjs --status success --message "Round completed" --critic-write-back --json
node scripts/harness-closeout-writeback.cjs --status failed --message "Round failed" --stage verification --json
node scripts/harness-critic.cjs --json
python3 scripts/check_harness_closeout_chain.py
./scripts/check_harness_governance.sh
./scripts/check_harness_governance.sh --with-cross-repo
./scripts/check_harness_governance_all.sh
```

These commands complement the Python runtime scripts under `scripts/runtime/`; they do not replace the Hermes-specific handoff and runtime-state workflow.

`record-success.cjs` / `record-failure.cjs` 现在只作为 `harness-closeout-writeback.cjs` 的底层 trace writer。对于非平凡迭代，不再允许把它们当成 direct closeout 入口；direct 调用只保留给显式 `--allow-trivial-direct --probe-reason ...` probe。`HARNESS_CLOSEOUT_CONTEXT` 也只保留给真实的 closeout 父进程，不接受环境变量伪装。

`status=success` 的 `harness-closeout-writeback` 默认会先执行全量治理检查 `./scripts/check_harness_governance_all.sh`。

当前全量治理检查会回写：

- `scripts/harness-doc-entrypoints.manifest.json`
- `docs/02-engineering/harness/harness-governance-report.md`
- `node scripts/harness-closeout-writeback.cjs` 生成的 closeout payload / harness trace 中的 `governanceReports`
- `harness/closeouts/*.json`

当 closeout / acceptance / deploy 结论需要组合判断时，还应参考：

- `FlowMindDeploy/docs/05-version-control/治理证据资产索引-v1-2026-05-07.md`
